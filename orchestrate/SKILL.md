# orchestrate

Central skill that runs the **plan / execute / integrate** cycle for batched, agent-driven implementation. Lives globally; reads a per-project overlay at `<home>/.claude/orchestrator/` for project specifics.

## Resolution: where am I, what do I read?

1. **Walk up from `$cwd`** looking for `.claude/orchestrator/config.yaml`. First hit wins; that directory is the **home** (`$ORCH_HOME`). It holds the process, `.orchestrator/` (one directory per change under `.orchestrator/changes/<change>/`: `change.json`, the event log, cycles, briefs, reviews, the inbox, the task files) and `.tasks/`, and its git repo tracks them. The home is usually a **workspace**, a directory holding worktrees of one or more repositories; a repository's root can be the home too (`overlay.md` § Repositories).
2. **Parse `config.yaml`** — required fields validated; missing-required = hard error. Optional fields fall through to core defaults.
3. **Read the repositories** from `config.yaml` (`repos:`, or the one-repository shorthands `code-root:` and the bare repository root; `overlay.md` § Repositories). A **change belongs to one repository** and is worked in its own worktree of it, on the branch named after the change, its **change integration branch**, which its tasks merge into. That worktree is the change's **code root** (`$CODE_ROOT`): where task worktrees branch from, code is merged and tested, and code commits are made. It also holds the **record**: `docs/specs/`, one org file per capability (`templates/spec.md`), and `docs/changes/<change>/` with the change's `intent.org` and `design.org`. `home.py open <name>` creates the worktree (or adopts one) and the change's directory; several changes may be open at once, each with its own directory and event log. When a hand-off produced several changes of one repository, they share a **workspace integration branch** (`research` § Hand-off): cut from the repository's main, carrying the glossary and the spec edits; each change is opened from it (`--from`, recorded in `change.json`), takes it in before its design round and before its whole-change review, and merges into it when done (`flows/design.md` § When it runs, `flows/integrate.md` § 9); its merge to main is the user's call. The orchestrator's cwd is the home, and every git or test command that belongs in the code root says so (`git -C "$CODE_ROOT"`, or a `cd` in a subshell). `eval "$(home.py where --sh)"` (`home.py` is `python3 ${CLAUDE_SKILL_DIR}/scripts/home.py`) exports `ORCH_HOME`, `ORCH_WORKTREES`, `ORCH_CHANGE`, `ORCH_CHANGE_DIR`, `ORCH_REPO` and `CODE_ROOT` for the resolved change; the flow docs write `<change-dir>` for `$ORCH_CHANGE_DIR`, the change's directory `<home>/.orchestrator/changes/<change>/`. Task worktrees are placed from the home by the overlay's `worktrees.pattern`, never under a code root (`home.py worktree <branch>` prints the path). A home or repository whose record is still under `openspec/` is converted first with the `openspec-convert` skill; `home.py where` warns.
4. **Append role overlays** from `<home>/.claude/orchestrator/roles/*.md` (if present) to the corresponding core role briefs at agent-spawn time, followed by `priors.md` (the user's standing rules, `overlay.md` § Priors) when it exists, and by the path of the product's glossary, `$CODE_ROOT/docs/glossary.org` (`templates/glossary.md`), and of any subject note it links, when it exists: the reference vocabulary for anything the agent writes that the user will read. Some agents start without the project's instructions, so the brief names it.
5. **No overlay found** → warn the user explicitly; fall back to sensible defaults (see `overlay.md`), or onboard the home with `home.py init` (`overlay.md` § Bootstrap). **An overlay that drifted** from the skill's schema (`home.py where` warns: a removed key, a retired concept in a role overlay, a `../` path to the home) is relayed to the user once and corrected by hand (`overlay.md` § Drift).

Full overlay contract: **[overlay.md](overlay.md)**.

## Before the first cycle: the design round

A change enters the orchestrator with its intent and its spec edits, committed in the code root: `docs/changes/<change>/intent.org` (`templates/intent.md`) and the requirements and scenarios it adds, changes or removes, edited in place in `docs/specs/` (`templates/spec.md`). The user may write both; otherwise an **opening** phase agent writes them from the user's words, `.tasks/` items or a split (`flows/open.md`). The Architect's **design round** (`flows/design.md`) then writes `docs/changes/<change>/design.org` (`templates/design.md`), Context, Decisions and the Seams table, and the pending tests the scenarios imply. It runs once per change, before the first `state.py cycle start`, and opens no cycle. The orchestrator does not write a design before the round, itself or through another agent: a change it opens or splits gets an intent and spec edits, and the round writes the design (`flows/design.md` § When it runs). Plan drafts tasks from the seams and the scenarios still pending; integrate checks merged code against them.

## Two contexts: the dispatcher and the phase agent

The session that invokes this skill is the **dispatcher**. It reads this file and the output of `state.py status` (the state layer: `python3 ${CLAUDE_SKILL_DIR}/scripts/state.py`, [state.md](state.md); the flow docs write it `state.py`, and its two neighbours `home.py` and `asks.py` the same way; every call writes it out in full, never through a shell variable: `S="python3 …"; $S status` reaches zsh as one word and exits 127, in all four homes on `cf2577d`), and of `report.py context` for a running phase agent (§ The dispatcher's loop), and nothing else: no flow doc, no role file, no artifact, no code; the one exception is an ask file it must put to the user, read once when `status` lists it (id, question, path), never the inbox in one `cat` (the record: five files at once, +14k context). Every phase runs in a **phase agent**, spawned with the `Agent` tool (`subagent_type: general-purpose`, at its role default, § Agent settings) from a fresh context, which reads its flow doc, spawns the role agents the flow names, runs the gate, makes the close commit and hands back one line. The dispatcher's context holds hand-back lines, the user's prompts and the blocking calls, so it stays near its floor for the whole change.

**`<skill-dir>`** in the flow, role, template and overlay docs is this skill's directory, `${CLAUDE_SKILL_DIR}` here (the installed tree, or a worktree run as the `dev` plugin by `bin/skill-dev`). Those docs are read as written, so a phase agent takes it from the path of its brief's flow doc, and writes it out in full in any brief it writes.

The record shows why: 82% of the orchestrator's context was accumulated history (235k tokens per call against a 45k floor); one session ran five cycles and reached 529k with four compactions; the main thread cost twice what all Implementors cost. A phase agent oriented in 64k in the dry run of 2026-10-13.

In the flow, role and template docs, **"the orchestrator" is the phase agent running that flow**; where the dispatcher is meant, it is named.

### The dispatcher's loop

1. `state.py status`: the change's `stage` and `next` step at every stage (not open, open with no intent, the design round, the MVP decision, a cycle open in plan, execute or integrate with that phase's gate, the main path ended, done), the inbox and the asks that block work, read from the change's files and git history; two sessions at one commit get the same answer. `home.py where` prints the home, its repositories and its open changes. With more than one change open, every `state.py` call names its change: `state.py --change <change> <verb>`, or `export ORCH_CHANGE=<change>` once; the flow docs write `state.py <verb>`. A call that cannot tell which change is meant refuses (`no_change`) and lists them.
2. Handle the inbox first if `status` lists an answered ask: that is a sync point (`templates/ask.md` § Sync points), done by the phase agent the next step spawns, not by the dispatcher.
3. Spawn the phase agent `status`'s `next` calls for: opening a change (`not open`, `open, no intent`; or the user asks for one, takes up `.tasks/` items, answers a split, or answers `rethink` on the MVP decision; the brief carries the source, `flows/open.md` § The brief; its agent runs `home.py open`, which makes the worktree), the design round (`intent, no design`), `plan` (including `state.py cycle start`), `execute`, `integrate` (including its close commit, and the MVP decision when `status` says the main path ended), or the inline path. A `next` that says to close a phase whose gate passed is the open phase agent's work: resume it, or spawn a fresh one for that phase. The `Agent` call passes the phase's role default as `model` and `effort` (§ Agent settings). The brief is fixed and short:

   > You are the phase agent for `<phase>` of change `<change>` in cycle `<cycle-id>` (or: for the design round of `<change>`). Home: `<path>`. `export ORCH_CHANGE=<change>`, then run `state.py status` (`state.py` is `python3 ${CLAUDE_SKILL_DIR}/scripts/state.py`, written out in full in every call, never through a shell variable), then read and follow `${CLAUDE_SKILL_DIR}/flows/<phase>.md` to its exit gate and close commit. Read a role file at the moment you spawn that role and a template at the moment you produce its artifact; do not read `SKILL.md`. Every agent you spawn runs at the agent setting the flow doc names at its spawn point: pass its `model` and `effort` on the `Agent` call, never neither, and its `description` as `<role>: <task-name>` (or `<role>: <cycle-id>` for an agent with no task). When nothing can run until a worker reports, end your turn with no hand-back; you are woken when the worker reports. You hand back once: at the phase's end, or on a stop. You cannot ask the user: an ask that would take the blocking call is a file, and you hand back `stopped` naming it after finishing everything that does not wait on it. Asked to hand over, you stop at a clean point and hand over as `flows/execute.md` § Handing over says, whatever your phase. Hand back one line (§ Hand-back lines), never a report. What the user reads uses the terms of `<code-root>/docs/glossary.org` (when it exists).

   A fresh agent for a phase that handed over gets the same brief with one more sentence: "Continue from `<handover path>`: read it after `state.py status`, and redo nothing it lists as done." It runs at the same role default as the agent it replaces.

4. On the hand-back: `state.py status` again. Gate passed → spawn the next phase agent. `stopped` on an ask → the inline rule (`templates/ask.md`): when the user is present, the dispatcher makes the blocking call for that one ask (one question per call), writes the answer with `asks.py set <id> decision=<label>` (or `status=answered` with the free text, for readback by the phase agent), and resumes the same phase agent by message so its context, worktrees and running workers are kept; when the user is absent, the dispatcher stops with the one-line pointer. `failed` → the line says what; the dispatcher reports it and stops. `stopped, handover <path>` → spawn a fresh agent for the same phase with the brief and its handover sentence (§ step 3). Design-round questions are ask files like any other, with `blocks: plan` (`flows/design.md` § 5): on `stopped, asks <ids> block plan` the dispatcher asks every one in one sitting, one per call, straight from `status`, and resumes the agent when all are answered; when the user is absent it stops with the pointer and the change waits. A round that hands back `stopped, <n> open questions` before any cycle exists has no cycle for their ids: spawn plan, whose agent starts the cycle and writes the files.
5. Relay to the user, after each hand-back: the line itself, then the open decisions. While the user is present they are put one per call, never as a list in chat: asks whose `:BLOCKS:` names work waiting now first, then the rest in `status` order, each call carrying the ask's recommendation and a `Not now` option that leaves the ask open (`templates/ask.md` § The inline rule). When the user is absent, they are relayed from `status` in one line each (id, question, path), and an ask that blocks nothing never stops the session. `process` asks are never put. The user answers in the call, the file or chat, and the dispatcher writes a chat answer with `asks.py set <id> decision=<label>` and a readback's yes with `asks.py set <id> readback=confirmed`, then commits the file. The record: four non-blocking asks once took the call after integrate, the dispatcher read the state tool's source to learn how a readback is confirmed, and the answers were left uncommitted; then, over the 56 cycles on `cf2577d`, the users asked again and again to go through the asks one at a time, the rule that only relayed them was broken in at least 116 calls in all four homes, and two dispatchers wrote the preference into memory.

A phase agent with workers still running does not hand back until they finish: a turn it ends to wait is not a hand-back, and a hand-back made while a worker runs reaches the dispatcher as if the phase had stopped. A hand-back that names a running worker or a wait (`__WAIT__`, "waiting on") is resumed by message. The record: in one home a design round, two executes and an integrate handed back while their workers ran, in 5 sessions over 4 changes. An ask raised mid-execute reaches the dispatcher when the running Implementors end, minutes later, with the merge chain already stopped as `flows/execute.md` § 9 says. Resume by message when the agent stopped on an ask; spawn fresh when it finished its phase.

**A phase agent near its context limit hands over to a fresh one.** At each hand-back and each turn a running phase agent ends to wait, before resuming it, the dispatcher runs `report.py context <agent-id>` (the id the `Agent` call returned; `report.py` is `python3 ${CLAUDE_SKILL_DIR}/scripts/report.py`): one line with the agent's context in tokens against the overlay's `thresholds.phase-agent-context` (default 400,000); it never reads the transcript itself. When `over` is true, the message that resumes the agent asks it to hand over: it starts nothing new, lets its running workers finish and merges what they land, then writes the handover file and hands back `stopped, handover <path>` (`flows/execute.md` § Handing over). The record: five phase agents in three homes passed 400k, the largest at 568,815; the users asked for a stop at about 400k and for "a checkpoint to swap in a fresh one", and ran two swaps by hand.

### Hand-back lines

Every agent the orchestrator spawns hands back **one line of at most 200 characters** and writes everything else to the file the flow names for it. A path in the line is relative to the home (`.orchestrator/changes/<change>/cycles/<id>/premise-check.md`), and a line whose file the brief named carries none (the Implementor's and the Reviewer's); the record: 13 of 14 role lines broke the limit with an absolute path of 149-170 characters, and after the relative rule 509 of 1,105 lines on `cf2577d` still did, the Implementor's and the Reviewer's with the absolute path their brief handed them. The line states the outcome and points at the file; the reader opens the file only when the next step needs it. The record: hand-backs and notifications carried 55% of the main thread's tokens.

| Agent | Line | Detail lives in |
|---|---|---|
| Phase agent | `<phase> <cycle-id>: gate passed` · `<phase> <cycle-id>: stopped, ask <id> blocks <task\|merge\|phase>; <path>` (several: `asks <ids> block …`) · `<phase> <cycle-id>: failed, <why>; <path>` · `<phase> <cycle-id>: stopped, handover <path>` (asked to hand over) · `inline <task>: bailed out, <why>; <task file>` (`flows/inline.md` § Bailout rule) · `plan: not started, change <stopped\|rethink>; <intent path>` (an MVP answer applied, `flows/plan.md` § 1) | the cycle's files, the event log, the ask file, `intent.org` |
| Opening agent | `open <change>: <c> capabilities, <s> scenarios, <q> open questions; <intent path>` · `open: failed, <why>` | `intent.org`, the spec edits, the `Open: <change>` commit |
| Implementor | `done <task> <sha>` with `deviated` / `candidates=<n>` appended when true · `blocked <task>: <one line>` · `failed <task>: <one line>` | `cycles/<id>/reports/<task>.md`, written by the Implementor; the task file's `## Observations` and `## Discoveries` |
| Reviewer | `reviewed <task> issues=<n> questions=<n> spec-signal=<n> thoughts=<n>` | `cycles/<id>/reviews/<task>.md`, the path the brief named |
| Architect | `design-round <change>: <n> seams, <k> pending tests, <u> uncited scenarios, <q> open questions` · `premise-check <cycle-id>: <n> holds, <m> wrong, <f> findings; <path>` · `conformance <cycle-id>: <f> findings, <a> rows amended; <path>` | `design.org`, `premise-check.md`, `findings/`, `design-diff.json` |

A worker runs its test command in the foreground and reports once, after its commit; a report sent while a run continues in the background wakes the orchestrator twice (8 such wake-ups in one session of the record).

### Phases

Each phase has its own flow doc and exit gate. **A phase is closed only once its gate passes**: the phase agent runs `state.py gate <phase>`, and on a pass commits `Orchestrator: <cycle-id> <phase> closed` in the home; `state.py status` reads the open phase from those commits and re-checks the gate each time it reports it (`state.md` § Stages, § Gates).

| Phase | Flow doc | Defining ops |
|---|---|---|
| Opening | [flows/open.md](flows/open.md) | Once per change the orchestrator opens: `intent.org` and the spec edits from the user's words, `.tasks/` items or a split, committed in the code root; no code read, no question asked (they join the round's sitting) |
| Design round | [flows/design.md](flows/design.md) | Once per change, before the first cycle: Architect writes `design.org` and the pending tests until `coverage.py --intent` shows no uncited scenario of the change's; open questions become ask files blocking plan, asked by the dispatcher |
| Plan | [flows/plan.md](flows/plan.md) | Consume prior integrate's handshake → draft candidate tasks from `design.org` and the pending scenarios → Architect premise check against HEAD → batch composition → implementor briefs |
| Execute | [flows/execute.md](flows/execute.md) | Per-task: worktree + Implementor + author-blind Reviewer (with probe licence); each task merged as it lands (serial chain) with regression check |
| Integrate | [flows/integrate.md](flows/integrate.md) | Design conformance (Architect) + meta-discovery and goal-drift recommendation (PM) + open-task refinement + handshake artifact + the `integrate closed` commit; the whole-change review at each integrate that merged code; when no task on the main path remains, the MVP decision, or done |

The state layer's verbs, the task statuses, the event log, the conventions and the exit gates: **[state.md](state.md)**.

If the work is trivially small (one-line edit, single-file doc fix, config tweak), use the inline path: **[flows/inline.md](flows/inline.md)**, run by a phase agent like any phase. Bailout to standard cycle if it grows.

The curation cycle (slower-tempo corpus grooming) is **deferred to v2**: see **[flows/curation.md](flows/curation.md)** for the placeholder and reasons.

## Agent settings

Every agent the orchestrator spawns runs at a chosen **agent setting**, its model and effort as a pair, never at the one it would inherit. Every `Agent` call passes both `model` and `effort`: this section is the instruction the `Agent` tool needs before it sets `effort`, which it does only when a skill asks, and it binds the dispatcher and every phase agent, whose flow docs name the setting at each spawn point. The record: all 15 spawn points named neither, so every agent ran at the dispatcher's model and effort, and a role agent at its phase agent's; one session ran Implementors on Fable until the user stopped it as more than the work needed (research `agent-model-effort`, E3).

The **role default** is the agent setting every agent of a role gets unless the plan says otherwise. `role` is the word the spawn's `description` starts with (§ Recording).

| Agent | Spawned by | `role` | Model | Effort | Why |
|---|---|---|---|---|---|
| Phase agent: opening | dispatcher | `phase-open` | `opus` | `medium` | Writes the intent and the spec edits every later role cites; 0.7% of spend |
| Phase agent: design round | dispatcher | `phase-design` | `sonnet` | `medium` | Spawns the Architect, runs `coverage.py`, commits; designs nothing |
| Phase agent: plan | dispatcher | `phase-plan` | `opus` | `medium` | Writes every task file: the batch from the design, the handshake's candidates, and each open task's refinement; task text is where most wrong premises in the record began (`flows/plan.md` § 3) |
| Phase agent: execute | dispatcher | `phase-execute` | `sonnet` | `high` | Coordinates by written rules: merges, tests, state, routing (a follow-up is a candidate, never a task file); the largest single spend (18%), at high effort for the merge and regression checks |
| Phase agent: integrate | dispatcher | `phase-integrate` | `sonnet` | `high` | Routes the Architect's and the Reviewer's findings by `templates/architect-finding.md`, and the user's answers, to candidates and impact sets for plan; the judgment is theirs, and it writes no task text (`flows/integrate.md` § 7) |
| Phase agent: inline path | dispatcher | `phase-inline` | `sonnet` | `medium` | One-file edits under a strict triage, bailing out when they grow |
| A fresh phase agent after a handover | dispatcher | the phase's | the phase's | the phase's | The same work |
| Architect: design round | design-round agent | `architect-design` | `opus` | `high` | Seams are the contract every later role cites |
| Architect: premise check | plan agent | `architect-premise` | `opus` | `medium` | A bounded, claim-by-claim check against HEAD |
| Architect: conformance | integrate agent | `architect-conformance` | `opus` | `high` | Decides whether the code or the design is right, and amends the contract |
| Implementor | execute agent | `implementor` | `opus` | `medium` | Writes the code; the plan lowers a routine task and raises a hard one |
| Implementor: rework, or fresh after a wrong premise | execute agent | `implementor-rework` | the task's | the task's | A retry runs at the same setting |
| Reviewer: per task | execute agent | `reviewer-task` | `opus` | `high` | Judges code; what it misses ships |
| Reviewer: whole change | integrate agent | `reviewer-whole-change` | `opus` | `xhigh` | The last gate before done, looking for what every per-task review missed |
| PM | integrate agent | `pm` | `sonnet` | `medium` | Meta-discoveries and the goal-drift recommendation for the handshake, read from the cycle's files; judges no code |

- **Quality first.** The roles where a mistake is expensive (the Architect, the Reviewer, and the opening and plan agents, which write the text everything after cites; the plan agent writes every task file, so no agent at a routing setting writes one) keep strong settings; cost and time are cut only where the work is routine. The phase agents mostly coordinate, and with the dispatcher they took 46% of spend in the record.
- **The range.** Opus and Sonnet at any effort; Fable only for a task the plan judges hard; Haiku only for a read-only helper (`web-fetch`, spawned with neither parameter, runs on its agent type's own Haiku), never for an agent that writes or judges code.
- **A task override** is the plan's change to one task's agent setting: it may raise or lower the task's Implementor, and raise its Reviewer, never lower it, writing the setting and a one-line reason in the task file (`flows/plan.md` § 5, `templates/task-body.md`). Nothing else changes a setting: no rule or model picks one, and a task that fails review or is reworked runs again at the setting it had.
- **The dispatcher's own setting is the user's** (`/model`, `/effort`); nothing here changes it. An alias names the dispatcher's own model when it is of that family: `opus` under Opus 5.5 is Opus 5.5.
- **Recording.** The spawn is the record. Every `Agent` call's `description` is `<role>: <task-name>`, the `role` from the table and the task the agent works on, or `<role>: <cycle-id>` for an agent with no task (a phase agent, the premise check, conformance, the whole-change review, the PM); an opening or design-round agent, which runs before any cycle, names the change: `phase-design: <change>`. The model and effort each request ran at are in the agent's transcript; a task override's reason is its task file's line. Nothing else is written. Work a phase agent does in its own context (the inline path's own review) runs at that phase agent's setting.
- **Spend and quality by role** are an on-demand report, `report.py spend` ([report.md](report.md)), run by the user or `/process-improvement`, never by a cycle: spend by role from the transcripts the descriptions name, the setting each agent ran at, and beside them Reviewer rejections, rework tasks and defects found after done, by the Implementor's setting. An environment variable (`CLAUDE_CODE_EFFORT_LEVEL`, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`) outranks the call; a task whose agent ran at another setting than its override is listed.

## Roles

The orchestrator deploys four roles. The phase agent reads the relevant role file before spawning; every role hands back one line (§ Hand-back lines):

- **[roles/implementor.md](roles/implementor.md)** — does the task at expert level in a worktree; produces diff + structured `## Observations` and `## Discoveries`; writes its report to `cycles/<id>/reports/<task>.md` for the orchestrator only (never the reviewer).
- **[roles/reviewer.md](roles/reviewer.md)** — author-blind review of one merged diff against the cited seam rows; rigorous-not-contrarian; may probe the merge candidate read-only. Author-blindness is kept by what the execute agent puts in the Reviewer's brief (`flows/execute.md` § 7); no code checks it.
- **[roles/architect.md](roles/architect.md)** — designs the seams that satisfy the spec and writes the pending tests (design round); checks the batch's premises at plan; checks merged code against the design at integrate and amends it. Three runs, no execute-time run.
- **[roles/project-manager.md](roles/project-manager.md)** — reads the cycle's files against the intent and writes the meta-discoveries and the goal-drift recommendation the handshake carries; computes no counts.

**Not every step needs an agent.** Triage inline-vs-worktree before spawning.

## Change artifact set

The record is in the code root, under `docs/`; the process is in the home, under `.orchestrator/`.

- **`docs/specs/`** is the one copy of the requirements and scenarios, an org file per capability, edited in place by each change on the branch its tasks merge into; `git diff <base> -- docs/specs/` is the change's spec record ([templates/spec.md](templates/spec.md)).
- **`design.org`** (`docs/changes/<change>/`) is the Architect's home: Context, Decisions and **Seams** (one row per contract between two parts of the code: id `seam/<name>`, statement, owning symbols, scenarios, tests). Rows hold current state only; the file's `git log` is the history. Template: [templates/design.md](templates/design.md).
- **Scenario coverage is computed, never written.** The tests cite `<capability> § <title>`, a scenario no test is worth writing for carries `:TEST: none: <reason>` in the spec, and `scripts/coverage.py` prints one row per scenario with its status (`templates/spec.md` § Coverage).
- **Pending tests** in the project's test tree, written by the design round for behaviour HEAD does not yet satisfy, marked with the overlay's `test.pending-style` (a style the runner reports as pending, never failing). Promotion is removing the marker, done by the Implementor in the commit that makes the test pass.
- **`intent.org`** (`docs/changes/<change>/`) carries what the diff cannot: why, goals, non-goals, capabilities, removals and their reasons, the new terms, a link to the research that preceded it, the change's `#+BASE:` and its `#+STATUS:` line ([templates/intent.md](templates/intent.md)). A done change stays where it is, its status line saying so.
- **`docs/glossary.org`** is the product's agreed terms, edited in place, the vocabulary of everything the user reads ([templates/glossary.md](templates/glossary.md)). A change's research, when it had any, is `docs/changes/<change>/research/` (the `research` skill).
- **The change's directory** is process: `<home>/.orchestrator/changes/<change>/` (`<change-dir>` in the flows, `$ORCH_CHANGE_DIR` in their shell) holds `change.json` (the repository, branch, worktree and base `home.py open` recorded), the event log `events.jsonl`, `cycles/`, `inbox/`, the handshakes and the test outputs (`state.md` § The change's directory). `home.py where` lists every open change's directory.
- **Task files** are process: `<change-dir>/tasks/open/` and `…/closed/` ([templates/task-body.md](templates/task-body.md)).
- **The hardening list** is process: `<home>/.orchestrator/changes/<change>/hardening.org`, the change's reasoned defects off the main path, shown to the user with the MVP ([templates/hardening.md](templates/hardening.md)).
- **Per-cycle Architect artifacts**: `cycles/<id>/premise-check.md` (plan § 3) and `cycles/<id>/design-diff.json` (integrate § 1).
- **Ask files**: one org file per question, `<change-dir>/inbox/<ask-id>.org` while open; `cycles/<id>/asks/<ask-id>.org` once applied, declined or superseded ([templates/ask.md](templates/ask.md)).
- **Provenance fields on every follow-up task**: `discovered_from`, `discovered_by`, `discovered_class`. `state.py check new` refuses a follow-up without the first two; placement by [externalisation.md](externalisation.md).

## Externalisation

In-change vs `.tasks/` rule: **[externalisation.md](externalisation.md)**. Rule of thumb: in-change tasks contribute to the intent's stated outcome; cross-cutting findings go to `.tasks/` with full provenance. Promotion back into the active change is the user's decision, on a `decision` ask (`externalisation.md` § Externalisation pressure).

## Loop closure: integrate → plan handshake

The keystone transition is **integrate → plan**, not execute → review. Each plan reads `<change-dir>/handshake-<prior-cycle-id>.json` as a hard input contract ([templates/handshake.md](templates/handshake.md)). Required fields: `design_diff`, `meta_discoveries`, `asks_for_user_open`, `asks_for_user_resolved`, `user_resolved_goal_drift`, `goal_drift_recommendation`, `task_refinements`, `candidate_tasks` and `journal`; no counts, ratios or signals. Empty list is allowed; missing field is not. Integrate writes it from the cycle's files, `state.py asks` and `state.py log`; its gate fails while a field is missing, and `state.py cycle start` refuses to start the next cycle on it.

This is the structural fix for "learns and forgets" — without it, the orchestrator becomes a queue runner.

## When NOT to use this skill

- Single ad-hoc edits with no batch context — just edit; don't bring in worktrees and agents.
- Projects with no test runner at all — the orchestrator can't validate anything. A project with one and no `.claude/orchestrator/config.yaml` in the repo or a workspace above it is onboarded first: `home.py init` with the user (`overlay.md` § Bootstrap), never a copy of another home's overlay.

## Mode detection at entry

When invoked without an explicit phase, the dispatcher runs its loop (§ Two contexts):

1. Run `state.py status`. Its `stage` and `next` say which phase agent to spawn (`state.md` § Stages): `not open` wants `home.py open` first (`flows/open.md` § 2; a change the user opened by hand, with its intent on its own branch, is adopted there with `--worktree`); `open, no intent` wants opening (`flows/open.md`); `intent, no design` the design round; `designed, no cycle open` a new plan phase, whose agent runs `state.py cycle start` (it reads the newest handshake, or none on a first cycle); `cycle open` the agent for its phase, which closes it when the gate passes; `main path ended` integrate's MVP decision; `MVP decision` waits for the user; `done`, nothing.
2. `convention_breaks` in `status`: the phase agent runs `state.py conventions` and fixes what it lists before the check that reads it (`state.md` § Conventions, § Recovery). Nothing is written to the event log by hand.

Never silently start a new cycle while a prior cycle is open; `state.py cycle start` refuses, and `state.py cycle abandon --why` is the explicit exit.

## Sync points

Where the orchestrator reads the inbox and what it does with an answered file there are listed once, in `templates/ask.md` § Sync points, which the phase agents read. The dispatcher only sees from `status` that an answer waits, and spawns or resumes the phase agent that handles it.

## Critical requirements

- **The dispatcher's context holds pointers only.** It reads `SKILL.md`, `state.py status` and `report.py context`; every phase runs in a phase agent from a fresh context (§ Two contexts). A dispatcher that reads a flow doc, a role file, an artifact or code is a process bug.
- **Every spawned agent runs at a chosen agent setting, and the record says which and why** (§ Agent settings). An `Agent` call with no `model` and `effort`, or whose `description` is not `<role>: <task-name | cycle-id | change>` (§ Agent settings, Recording), is a process bug; the one exception is a read-only helper on its own agent type (`web-fetch`), spawned with neither and named as it likes.
- **Every spawned agent hands back one line; the detail is a file** (§ Hand-back lines). A report, a findings list or a narrative in a hand-back is a process bug; the orchestrator opens the file when the next step needs it.
- **Files and git are the record; the state layer writes only the event log.** There is no state file. A task's status is its task file's `status:`, written by the orchestrator after the check that guards it (`state.py check start`, `check done`, `check new`); a merge is its `Merge task <name>` commit; a phase's close is its home commit; an ask is its file. The event log is written only through `scripts/state.py`; a heredoc, `jq`, `sed` or Write against it is a process bug. A fact copied to a second place (a `merge_commit` in a task file, a `decoration` in a finding file) is a process bug (`state.md`).
- **Done is computed.** A task, gate or phase passes only on computed checks; an asserted check shows as asserted, with who and when. No count, ratio or signal is computed each cycle; spend and quality are `report.py spend`, on demand.
- **Author-blind review is prose, kept by the execute agent.** The Reviewer's brief carries no path to the Implementor's report, observations, discoveries, identity or scratch files (`flows/execute.md` § 7). No code checks it.
- **The design is the contract, and holds only contracts.** Tasks cite seam rows, briefs and reviews quote them, and integrate's conformance check amends them when the code has rightly outgrown them. Nothing else catalogues interfaces. A row or Decision that names a guard, error string, encoding, helper or test is wrong by construction and is cut, not amended (`templates/design.md`). A stale row or sentence beside right code is a **record correction**: fixed, committed, one journal line; never an ask.
- **Phase exit gates are mandatory.** A phase is closed only after `state.py gate` passes, and the next starts from that close commit.
- **Every code change takes one of three paths**: a batch task (Implementor + author-blind Reviewer), the inline path (`flows/inline.md`, within its triage), or an inline fix for a review finding or a simple main-path discovery (`flows/execute.md` § 8, § 5). The orchestrator never edits the code directly, not to apply an ask's answer, not to add scope to a running task; the one exception is a text correction, prose only (`templates/architect-finding.md` § Routing). The record under `docs/` is not code: the design round, an applied answer, a record correction and integrate write it in the code root, the change's worktree; an Implementor never does. **A change is reported done only after the whole-change review** (`flows/integrate.md` § 9) has run and its blocking findings are resolved.
- **Provenance fields are mandatory on follow-up tasks.** `state.py check new` refuses one without them, and the orchestrator does not externalise one.
- **The integrate→plan handshake artifact is the loop-closure contract.** Without every required field (`templates/handshake.md`), `state.py cycle start` refuses.
- **Scope takes the YAGNI check; defects are reported and routed, never dropped.** A feature, option, generalisation or question to the user earns work only when an intent goal needs it or on a demonstrated reason (it happened, a prior, the user asked, a measured cost); otherwise it is not built and not asked about, and an agent that thinks it matters writes one `thought` line. Every defect an agent finds in code or text that exists is reported with a kind (`issue`, `question`, `thought`) and severity, whatever its likelihood; the orchestrator alone routes it: on the change's main path (the uses the intent's goals name) it is reproduced and fixed in the change, an untrue sentence in a shipped document is fixed in the change, anything else goes on the change's hardening list. The one statement is `templates/architect-finding.md`. The user's own words (a prior, an ask decision, an intent sentence) outrank a `design.org` sentence.
- **A change produces a working MVP first, then stops for the user.** When the main path works end to end (no task on it open, whatever else the change still holds; `flows/plan.md` § 6), the change asks one `decision` (harden / rethink / stop) carrying the hardening list and every spec correction made as a record correction, and nothing more runs until the user answers (`templates/hardening.md`). Hardening is worked only after the user chooses it.
- **The glossary is the vocabulary of everything the user reads**: asks, hand-back lines, relays and chat. A domain term it does not have is glossed where it is used, or added to `$CODE_ROOT/docs/glossary.org` first (`templates/glossary.md`). When the user asks what a term means, the explanation is written into the glossary in the same turn and committed in the code root; an explanation given only in chat is lost by the next phase. No check runs against the glossary until a misuse is observed.
- **Every question to the user is an org file in `<change-dir>/inbox/`** per `templates/ask.md`, written the moment it is raised, in any phase, and triaged by kind. Only `decision` kinds reach the user as questions; the user answers in the file; an answer outside the offered options is read back before it is applied. When a question blocks the session is stated once, in `templates/ask.md` § The inline rule; the call is the dispatcher's, since a phase agent has no user (§ Two contexts). Nothing else blocks a session on a question.
- **Process artifacts are tracked in git, in the home repo.** `.orchestrator/` is never gitignored there (`home.py open` writes `.orchestrator/.gitignore` for the test outputs, and refuses a code root holding a `.orchestrator/` of its own). When the orchestrator commits is listed once, in `templates/ask.md` § Commit rule. Process commits are made in the home; record (`docs/`) and code commits in the code root. The home's `.gitignore` ignores the worktrees folder and any repository checkout nested inside the home (`home.py where` warns when it does not), so no code checkout appears as an embedded repository in the home's history.
- **When the home and the code root differ, "in one commit" means one commit per repository.** Every rule that says so (an applied ask: its file moves in the home, the edit it applies lands in the code root) is then one commit in each repository with the same subject, the code-root commit's message naming the ask id or the change. The record and the code share the code root, so the design round's `design.org` with its pending tests, and a record correction with its edit, are one commit there.
