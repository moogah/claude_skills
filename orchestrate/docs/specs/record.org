* Purpose

The record is where a change's process is kept in the home: the change's own directory, the files the
roles write there, the home's commits, and the event log, which holds the few facts files and git do
not. Other capabilities state that something is recorded ("the change's record shows the regression
against the task", "the change's journal records the cause"); this spec states where and in what form,
so that what they record can be found and read. Every fact has one source; nothing in the record is a
second copy of another fact.

It covers the change's directory and the cycle's directory, the event log and who writes it, a task's
status and what it rests on, where a change stands and what comes next, each phase's gate and its
checks, the handshake integrate leaves for the next plan, when a cycle may start and what closes it,
how the spawned agents are recorded, the forms the record is read by, and how a lost or older record is
recovered. It does not say when a phase runs, what a phase decides or what an ask file holds: those are
the phases' specs and =asks='s.

* Requirements

** Requirement: A change has a directory of its own in the home
:PROPERTIES:
:GOAL:     none stated
:END:
Each open change SHALL have one directory in the home, named for the change, holding its process
files. The home's git SHALL track that directory, except the output of test runs and temporary files;
the exit codes of the test runs SHALL be tracked.

*** Scenario: The change's directory is named for the change, under the home
- *WHEN* a change is open
- *THEN* its process files are in =.orchestrator/changes/<change>/= under the home
- *AND* that directory holds the change's event log, its cycles, its inbox of asks, its handshakes, its task files and its test runs

*** Scenario: The change's directory is tracked by the home, its test runs are not
- *WHEN* the home's git is asked what it tracks under =.orchestrator/=
- *THEN* it tracks the change's directory, the test runs' exit codes among it
- *AND* it ignores the test runs' output and temporary files

** Requirement: Files and git are the record, and the state layer writes only the event log
:PROPERTIES:
:GOAL:     none stated
:END:
A change's state SHALL be read from the files the roles write and from git, each fact from one source.
There SHALL be no state file. The state layer SHALL write one file, the change's event log, and only
through its commands.

*** Scenario: No state file is written
- *WHEN* a cycle runs from plan to close
- *THEN* no =state.json= exists in the change's directory
- *AND* the only file the state layer wrote is the event log, =events.jsonl= in the change's directory

*** Scenario: A fact has no second copy
- *WHEN* a task has merged and a finding has been routed
- *THEN* the task's merge commit is read only from its merge commit on the change branch, and its task file has no =merge_commit= field
- *AND* the finding's routing and resolution are read only from the event log, and its finding file has no =decoration= or =resolution= field

*** Scenario: No role edits the event log by hand
- *WHEN* any role adds to the event log
- *THEN* it does so through a state tool command
- *AND* never by writing the file with an editor, a heredoc or a text filter

** Requirement: The event log is append-only
:PROPERTIES:
:GOAL:     none stated
:END:
The event log SHALL hold one entry per line, each with its sequence number, its time, its cycle and its
kind. An entry SHALL never be changed or removed; a correction SHALL be a new entry naming the entry it
corrects, and every reader SHALL apply it.

*** Scenario: A wrong entry is corrected by a new entry
- *WHEN* a finding is routed =blocking= with resolution =pending= by mistake and a correction naming that entry is recorded
- *THEN* the log holds both entries
- *AND* every answer that reads the routing, integrate's gate among them, counts no pending blocking finding for it

*** Scenario: A cycle's start is in the log before any artifact
- *WHEN* a cycle has started and nothing of it is yet on disk or in git
- *THEN* the answer to where the change stands names the open cycle, read from the log

** Requirement: The journal holds short narrative, each line against what it concerns
:PROPERTIES:
:GOAL:     none stated
:END:
The event log SHALL hold the change's journal: one note entry per piece of short narrative that has no
other home (a discovery, a decision, an inline fix, a deviation from the flow, a push-back, a note),
each naming its kind and what it concerns, in one line, with any longer form in a file.

*** Scenario: A journal entry names its kind and what it is against
- *WHEN* a role records a discovery, a decision, an inline fix, a deviation, a push-back or a note
- *THEN* the event log gains one note entry whose kind is that kind, whose text is one line and whose time is when it was written
- *AND* its =ref= names the task, finding, ask or seam it is against, when it is against one

*** Scenario: A journal entry names who wrote it
- *WHEN* a journal entry is written
- *THEN* its =by= names who wrote it: =orchestrator= (the phase agent), =implementor=, =reviewer=, =architect= or =pm=
- *AND* any other =by= is refused

*** Scenario: A journal line is short, and the long form is a file
- *WHEN* what a role has to record runs longer than one line
- *THEN* the journal entry's text is at most 280 characters, and a longer one is refused
- *AND* its =path= names the file that holds the rest

*** Scenario: A regression is a journal line against the task, with the run that shows it
- *WHEN* a merge causes a regression
- *THEN* the journal gains a =discovery= entry saying so, its =ref= the task whose merge caused it
- *AND* its =path= names the run after that merge

** Requirement: The record's files, commits and event log are its boundary
:PROPERTIES:
:GOAL:     none stated
:END:
What another role, or an eval, may rely on in the record SHALL be the change's directory and the names
this spec gives in it, the task files' frontmatter keys it names, the commit subjects it names, and the
event log's kinds and fields it names. The rest is the state layer's own. A tool that changes a named
form changes this spec.

*** Scenario: A reader finds a task's facts by the fields the record names
- *WHEN* a reader outside the state layer needs to know a task's status, its merge, whether its tests passed at the merge, whether a regression was recorded against it, or what the journal holds against it
- *THEN* it reads the task file's frontmatter, the change branch's merge commit for the task, the exit codes recorded for that merge and the event log's note entries
- *AND* it needs nothing else

** Requirement: Where a change stands is one answer, read from the record
:PROPERTIES:
:GOAL:     none stated
:END:
The state layer SHALL answer, in one read-only call that needs no open cycle, the change's stage, its
next step, the open cycle and its phase, and the asks still waiting, those that block work first. The
answer SHALL be the same for any session that asks at the same commit.

*** Scenario: A change with no design gets the design round
- *WHEN* a change is open with an approved intent, and its design has no seam row
- *THEN* the answer's stage is that the intent has no design
- *AND* its next step is the design round

*** Scenario: An open cycle resumes at its phase
- *WHEN* a cycle is open and the home's last commit for it closed its plan
- *THEN* the answer names the open cycle in execute
- *AND* its next step is to resume execute

*** Scenario: The main path's end calls for the MVP decision
- *WHEN* no open task is on the main path, at least one task is, and the intent's status line is neither =mvp= nor =done=
- *THEN* the next step is integrate's MVP decision
- *AND* it is not a new plan

*** Scenario: A waiting MVP decision is a wait
- *WHEN* the intent's status line is =mvp= naming an ask, and that ask has no answer
- *THEN* the next step is to wait for the user's answer to that ask

*** Scenario: Two sessions get the same answer
- *WHEN* two fresh sessions ask for the same change at the same commit
- *THEN* both receive the same stage and next step

** Requirement: Each open change has its own record
:PROPERTIES:
:GOAL:     none stated
:END:
Each open change SHALL have its own directory and event log, so that several changes run their cycles
side by side, and a cycle SHALL be named =cycle-<unix-ts>=.

*** Scenario: Each open change has its own record
- *WHEN* two changes of one home are open
- *THEN* each has its own event log, in its own change's directory
- *AND* a cycle of one runs while a cycle of the other is open

*** Scenario: The open cycle and its phase are read from the log and the home's commits
- *WHEN* a cycle of a change is open
- *THEN* its id, =cycle-<unix-ts>=, is that of the log's last cycle start with no close and no abandonment
- *AND* its phase is the first of =plan=, =execute= and =integrate= with no commit in the home closing it

** Requirement: Narrative lives in files of its own
:PROPERTIES:
:GOAL:     none stated
:END:
Narrative longer than a journal line SHALL be a file of its own in the change's or the cycle's
directory, and the record SHALL hold no prose in place of one.

*** Scenario: Narrative is a file of its own
- *WHEN* a role has narrative to keep that is longer than a journal line: a finding, a review, an ask's prose, a brief, a report
- *THEN* it is in a file of its own
- *AND* a journal line about it names that file by its path

** Requirement: A task's status is in its task file, and changes only where a check allows
:PROPERTIES:
:GOAL:     none stated
:END:
A task's status SHALL be its task file's =status:=, one of a closed set, and nowhere else. A task SHALL
start only once every task it waits for has merged, and SHALL be =done= only on computed checks: its
merge commit on the change branch, a review naming that commit, and its tests passing there. A task's
task file SHALL also hold what its status rests on that no other source holds: what it waits for,
whether it is on the main path, and, for a task whose source is another task or a finding, where it came
from.

*** Scenario: A task's status is its task file's, one of seven
- *WHEN* a task is in the change's record
- *THEN* its task file's =status= is one of =ready=, =in_progress=, =needs_review=, =done=, =failed=, =blocked= and =externalised=
- *AND* a value outside them is reported as a break of the record's forms

*** Scenario: A task starts only once its blockers merged
- *WHEN* a task's start is asked for while a task its =blocked_by= names has no merge commit on the change branch
- *THEN* the state layer refuses, naming that task
- *AND* once every task it names has merged, the task may start

*** Scenario: A task awaits review only with its merge commit recorded
- *WHEN* a task's status is =needs_review=
- *THEN* the change branch holds the task's merge commit, =Merge task <task>=
- *AND* the review file names the commit the Reviewer read: that merge, or, when a regression it caused was fixed, the code root's commit after the fix

*** Scenario: Done without a merge is refused
- *WHEN* a task's move to =done= is checked and the change branch has no merge commit for it
- *THEN* the state layer refuses, naming the missing merge

*** Scenario: Done without a review is refused
- *WHEN* the task has a merge commit and no review file names it
- *THEN* the state layer refuses, naming the missing review

*** Scenario: Done without a test run is refused
- *WHEN* a task has its merge commit and a review naming it, and no exit code is recorded for the run after that merge
- *THEN* the state layer refuses, naming the missing file

*** Scenario: Failing tests on a green baseline are refused
- *WHEN* the cycle's baseline exited 0 and the task's run after its merge exited non-zero
- *THEN* the state layer refuses, naming the run

*** Scenario: A red baseline is read through the comparison
- *WHEN* the cycle's baseline exited non-zero and the task's run exited non-zero
- *THEN* the task may be =done= only when the recorded comparison of the two runs holds 0
- *AND* a missing or non-zero comparison is refused, naming it

*** Scenario: A send-back is a rework brief and review of the task
- *WHEN* a review sends a task back
- *THEN* the cycle's directory gains a rework brief and, once reviewed again, a rework review for that task, each a file of its own
- *AND* no counter of send-backs is kept

*** Scenario: A task blocked on an ask names the ask
- *WHEN* a task is blocked on an ask
- *THEN* its task file's =status= is =blocked=
- *AND* the event log's blocker note for the task is the ask's id

*** Scenario: A task names the tasks it waits for
- *WHEN* a task depends on other tasks of the change
- *THEN* its task file's =blocked_by= lists their names

*** Scenario: A task on the main path is marked in its task file
- *WHEN* a task is on the change's main path
- *THEN* its task file's =on_critical_path= is true
- *AND* it is false on every other task

*** Scenario: A task whose source is another task names where it came from
- *WHEN* a task's source is another task or a finding
- *THEN* its task file's =discovered_from= and =discovered_by= are set, and =discovered_class= where it was given

*** Scenario: A follow-up without its source is refused
- *WHEN* plan writes a task from a handshake's candidate and its task file has no =discovered_from=
- *THEN* the state layer refuses it, naming the missing field

** Requirement: A finding's routing and resolution are in the event log
:PROPERTIES:
:GOAL:     none stated
:END:
Each finding SHALL be a file of its own, its fields the =reviewer= spec's. Its routing and how it was
resolved SHALL be entries in the event log, the latest of each counting.

*** Scenario: A finding's routing and resolution are entries in the event log
- *WHEN* a finding in a file of its own is routed or resolved
- *THEN* the event log gains an entry naming the finding with its routing, =blocking= or =hardening=, and its resolution
- *AND* its resolution is =pending= until it is resolved, the latest entry counting
- *AND* a finding routed to a =decision= ask stays =pending= until the ask is applied, when the orchestrator routes it again; the ask's =:REF:= names the finding

*** Scenario: A finding's resolution is one of a fixed list
- *WHEN* a finding is resolved
- *THEN* its resolution is one of =inline-fixed=, =design-amended=, =candidate-task-<name>=, =followup-task-<task-name>=, =reverted=, =accepted-with-note= or =hardening-list=
- *AND* any other value is refused

** Requirement: Each phase passes its gate before the next phase starts
:PROPERTIES:
:GOAL:     none stated
:END:
Each phase of a cycle SHALL have a gate: its named checks. A gate SHALL pass only when every computed
check holds and every asserted check has been asserted in that cycle and phase, and a phase SHALL be
closed only once its gate passes. A computed check SHALL be decided afresh from the files and git each
time the gate is reported; an asserted check SHALL be shown as asserted, with who asserted it and when.
Each phase's checks SHALL be those this requirement names.

*** Scenario: A phase moves on only after its gate passes
- *WHEN* a phase's gate has a check that does not hold
- *THEN* no commit in the home closes that phase
- *AND* the change's stage stays at that phase

*** Scenario: A passed gate is re-checked each time it is reported
- *WHEN* execute's gate passed and a task's merge commit is afterwards removed from the change branch
- *THEN* the next report of the gate shows it failing, naming the task

*** Scenario: A check the record can show is computed, never asserted
- *WHEN* a check is one the files and git can show
- *THEN* it holds only when they show it
- *AND* an assertion of it is refused

*** Scenario: An asserted check gives its reason in the journal
- *WHEN* the phase agent asserts a check the record cannot show (the batch composed, the open tasks refined)
- *THEN* the event log holds the assertion with who asserted it and when, and every report of the gate shows it as asserted, never as computed
- *AND* any reason for it is a journal entry

*** Scenario: Plan's gate checks the handshake, the batch, its citations and the goal-drift answer
- *WHEN* plan passes its gate in a cycle after the change's first
- *THEN* the prior cycle's handshake had every required field (=prior_handshake_complete=, computed)
- *AND* the batch was declared composed (=batch_composed=, asserted)
- *AND* the batch is not empty, every brief in it has its task file, and every task in it cites a seam (=batch_cites_seams=, computed)
- *AND* every follow-up in it names its source (=follow_ups_name_their_source=, computed)
- *AND* no goal-drift ask waits unanswered or answered with anything but one of its four labels (=goal_drift_signed_off=, computed)
- *AND* the main path has not ended (=mvp_decision_not_due=, computed)

*** Scenario: On a first cycle, plan's gate asks for no handshake
- *WHEN* plan passes its gate in a change's first cycle
- *THEN* its handshake check holds with no handshake

*** Scenario: The goal-drift check holds only on one of its four answers
- *WHEN* the prior integrate raised a goal-drift ask
- *THEN* plan's gate passes only once that ask's answer names =revise=, =split=, =abandon= or =continue= exactly

*** Scenario: Execute's gate checks that every task ended and every review is filed
- *WHEN* execute passes its gate
- *THEN* the batch is not empty and every task in it is =done=, =failed=, =blocked= or =externalised= (=batch_stopped=)
- *AND* every =done= task in it is merged, reviewed at its merge and passing its tests there (=done_tasks_merged_and_reviewed=)
- *AND* every merged task merged after each task its =blocked_by= names (=blocked_by_order=)
- *AND* all three checks are computed

*** Scenario: Integrate's gate checks the findings, the asks, the open tasks and the handshake
- *WHEN* integrate passes its gate
- *THEN* no finding routed blocking is pending (=blocking_findings_resolved=, computed)
- *AND* the handshake is written with every required field, its candidates and design-diff entries in form, and a candidate for every finding resolved =candidate-task-<name>= (=handshake_written=, computed)
- *AND* every open ask is in the handshake's open asks and no open ask has an answer without its readback (=asks_routed=, computed)
- *AND* every open task has its entry in the handshake's task refinements (=open_tasks_refined_against_handshake=, asserted)

** Requirement: Integrate leaves a handshake the next plan reads
:PROPERTIES:
:GOAL:     none stated
:END:
Integrate SHALL leave in the change's directory a handshake for its cycle, a file named for the cycle,
holding nine required fields, each present even when it has nothing to carry. Its fields SHALL carry
what this requirement names, and no count, ratio or signal.

*** Scenario: The handshake is a file of the change's directory, named for its cycle
- *WHEN* integrate writes its cycle's handshake
- *THEN* it is =handshake-<cycle-id>.json= in the change's directory

*** Scenario: The handshake holds nine required fields, each present even when empty
- *WHEN* a handshake is written
- *THEN* it holds =design_diff=, =meta_discoveries=, =asks_for_user_open=, =asks_for_user_resolved=, =user_resolved_goal_drift=, =goal_drift_recommendation=, =task_refinements=, =candidate_tasks= and =journal=
- *AND* a field with nothing to carry is empty, never left out
- *AND* it holds no count, ratio or signal

*** Scenario: The handshake carries the cycle's journal
- *WHEN* a handshake is written
- *THEN* its =journal= is the cycle's note entries from the event log

*** Scenario: The handshake names each seam row that moved
- *WHEN* a handshake is written after a cycle that added, amended or retired seam rows
- *THEN* each entry of its =design_diff= names a seam row (=seam=), how it changed (=change=) and the finding or ask behind it (=ref=)

*** Scenario: The handshake lists the open asks, and the settled ones with their decisions
- *WHEN* a handshake is written
- *THEN* its =asks_for_user_open= holds each open ask with its kind, what it blocks and the path of its file
- *AND* its =asks_for_user_resolved= holds each ask whose file the home's git touched since the cycle started, and each answered or deferred one still in the inbox, with its decision, its readback and what applied it, read from its file

*** Scenario: The resolved asks are the cycle's
- *WHEN* integrate gathers the handshake's resolved asks, one ask was applied in an earlier cycle and one in this cycle
- *THEN* only the one whose file the home's git touched since this cycle started is listed, wherever its file now sits

*** Scenario: A goal-drift answer is carried with its label and its readback
- *WHEN* the user has answered a goal-drift ask in the cycle
- *THEN* the handshake's =user_resolved_goal_drift= holds the ask's id, the label the answer named (=revise=, =split=, =abandon= or =continue=) and the readback as its rationale

*** Scenario: The PM's goal-drift recommendation is carried with its reason
- *WHEN* a handshake is written
- *THEN* its =goal_drift_recommendation= holds the PM's recommendation, =none=, =revise=, =split=, =abandon= or =continue=, and its one-line reason

*** Scenario: A follow-up candidate in the handshake carries its source's words
- *WHEN* a follow-up candidate is in the handshake's =candidate_tasks=
- *THEN* it has its =name=, its =source=, who found it (=discovered_by=), whether it is =critical= and the source's words verbatim (=quote=)
- *AND* it has nothing else but, where given, =discovered_class=, =evidence= and =placement=

*** Scenario: Each open task's refinement names what touched it
- *WHEN* a handshake is written
- *THEN* its =task_refinements= has one entry per open task of the change, naming the task's file, its =impact= as a list of channels and refs, and whether it is flagged as possibly obsolete
- *AND* a task nothing touched has an empty =impact=

** Requirement: A cycle starts only when the record can hold it
:PROPERTIES:
:GOAL:     none stated
:END:
A new cycle of a change SHALL start only when no cycle of that change is open, the change is designed
and its main path has not ended, and the newest handshake is present with every required field (or no
cycle of the change has closed). A cycle's start SHALL be an entry in the event log naming the
handshake it started from.

*** Scenario: No cycle starts while one is open
- *WHEN* a cycle of a change is open
- *THEN* no new cycle of that change starts
- *AND* the event log gains nothing

*** Scenario: No cycle starts in a home whose git ignores the record
- *WHEN* the home's git ignores =.orchestrator/=
- *THEN* no cycle starts

*** Scenario: No cycle starts while the code root holds a record of its own
- *WHEN* the change's code root holds an =.orchestrator/= directory of its own
- *THEN* no cycle starts

*** Scenario: No cycle starts without the prior handshake
- *WHEN* a cycle of the change has closed and the newest handshake is missing or lacks a required field
- *THEN* no new cycle starts, and the refusal names each missing field

*** Scenario: A change's first cycle starts with no handshake
- *WHEN* a change's first cycle starts
- *THEN* no handshake is needed
- *AND* its start entry in the event log names no prior handshake

*** Scenario: A later cycle's start names the handshake it started from
- *WHEN* a cycle other than the change's first starts
- *THEN* its start entry in the event log names the newest handshake in the change's directory

*** Scenario: No cycle starts before the design or after the main path ended
- *WHEN* the change has no seam row in its design, is =done=, waits on its MVP decision, or its main path has ended
- *THEN* no cycle starts, and the refusal names the change's stage

** Requirement: Closing a cycle is a commit, and nothing is archived
:PROPERTIES:
:GOAL:     none stated
:END:
A cycle SHALL close only once integrate's gate has passed, by the commit closing its integrate, with its
handshake written, unless it is explicitly abandoned. Nothing SHALL be moved or copied at the close;
every artifact stays where the step that wrote it put it, under the names this requirement gives.

*** Scenario: A cycle closes only after integrate's gate passes
- *WHEN* integrate's gate has not passed and the cycle is not being abandoned
- *THEN* the cycle stays open

*** Scenario: An abandoned cycle's reason is in the event log
- *WHEN* a cycle is ended as abandoned, with a reason
- *THEN* the event log gains an entry saying the cycle was abandoned and giving the reason
- *AND* the cycle is no longer open

*** Scenario: Closing a cycle archives nothing
- *WHEN* a cycle closes
- *THEN* the change's directory holds =handshake-<cycle-id>.json=, and nothing of the cycle is moved or copied
- *AND* no state file is written in the cycle's directory

*** Scenario: A cycle's directory holds what its steps wrote, under fixed names
- *WHEN* a cycle has run
- *THEN* its directory is =.orchestrator/changes/<change>/cycles/<cycle-id>/= in the home
- *AND* it holds what the cycle's steps wrote, each under its name: the Implementors' briefs (=briefs/<task>.md=), their reports (=reports/<task>.md=), the review files (=reviews/<task>.md=, and =reviews/whole-change.md=), the findings (=findings/<finding-id>.md=), the settled asks (=asks/<ask-id>.org=), =premise-check.md=, =design-diff.json=, =meta-discoveries.json=, =task-refinements.json= and =candidate-tasks.json=

*** Scenario: The change's directory holds its files under fixed names
- *WHEN* a change is open
- *THEN* its directory holds =change.json= (the repository, branch, worktree and base commit the change was opened on), =events.jsonl= and the inbox, =inbox/=
- *AND* a =handshake-<cycle-id>.json= for each cycle whose integrate wrote one
- *AND* the task files under =tasks/open/= and =tasks/closed/=, and the hardening list, =hardening.org=
- *AND* the baseline's exit code, =baseline-<cycle-id>.status=, and for each run after a merge its exit code, =after-<task>-<sha12>.status=, and against a red baseline its comparison's, =.compare=, each beside its output, =.txt=

*** Scenario: The change's directory holds what the design round leaves before any cycle
- *WHEN* the design round has run
- *THEN* the change's directory holds the Architect's brief, =briefs/design-round.md=, and for each re-run =briefs/design-round-<seam-id>.md=, the seam id's slash written as a dash (=briefs/design-round-seam-on-screen.md= for =seam/on-screen=)
- *AND* each finding the round reported, =findings/<finding-id>.md=, outside any cycle

** Requirement: The record is committed in the home at each phase's close
:PROPERTIES:
:GOAL:     none stated
:END:
What the change's directory holds and the home's git tracks SHALL be committed in the home no later
than the close of the phase that wrote it, in one commit whose subject names the cycle and the phase.
That commit SHALL be what records the phase's close; a subject in another form SHALL NOT be read as one.

*** Scenario: Each phase's close commits the record in the home
- *WHEN* a phase of a cycle closes
- *THEN* one commit in the home, subject =Orchestrator: <cycle-id> <phase> closed=, holds the event log and whatever else the phase wrote in the change's directory that was not yet committed

*** Scenario: A phase is closed only by its closing commit
- *WHEN* the home has a commit for a cycle's phase whose subject is not exactly =Orchestrator: <cycle-id> <phase> closed=
- *THEN* the phase is not read as closed

** Requirement: The record's forms are checked, and a break fails what reads it
:PROPERTIES:
:GOAL:     none stated
:END:
The state layer SHALL check the forms the record is read by: the merge commits on the change branch,
the phase-close commits, the inline-fix commits, the test runs' files, the review and brief files, and
the task files' frontmatter. It SHALL report each break with where it is and the form expected, and a
break in a form a computed check reads SHALL fail that check rather than be guessed around.

*** Scenario: A merge commit in another form is reported
