#+TITLE: Glossary
#+OPTIONS: ^:{} -:nil

The orchestrate skill's agreed terms. The eleven below were agreed during the research effort =~/emacs-workspaces/claude-skills/research/skill-evals/= (2026-11-11). The =state-layer= branch adds this file too, with its own terms; when the two meet, the file holds both sets.

The orchestrate terms below the evals' were drafted from the reference skill (=main= =e356da7=) and agreed with the user at the hand-off review of the =execute= spec, 2026-11-13; the draft, with each entry's source in =main=, is =research/skill-evals/glossary-draft.org=.

* outcome
Something =orchestrate= is supposed to result in that the user would notice without reading the skill text. Since 2026-11-12 the outcome list (=docs/outcomes.org=) is source material for the spec, and a requirement's =:GOAL:= carries the trace up to the north star.
- Example :: "It would be better to establish a list of behaviors the orchestrate skill is supposed to result in, and have evals for those."
- Avoid :: goal (the north star's word, for a whole change or many), requirement, behaviour (used loosely for both an outcome and a rule)
- Specs :: skill-evals

* rule
Retired 2026-11-12. In a spec, what a rule stated is a requirement or a scenario (=templates/spec.md=); a sentence of the skill text cited as the origin of a backfilled statement is a quote in its extraction record.

/As agreed 2026-11-11:/ An instruction in a flow or role doc that an agent must follow; how the skill produces an outcome.
- Example :: a hand-back is one line of at most 200 characters.
- Avoid :: behaviour
- Specs :: skill-evals

* interface artifact
A file one step of the skill writes and another step, usually of a different role, reads as its input; the place where work passes between agents.
- Example :: "These 'interface artifacts' are an important part of the design of this skill and fundamentally how we spread complex work across many agents with different roles."
- Avoid :: hand-off (research's word), contract (harness-design's word, for a dependency)
- Specs :: skill-evals

* rubric
The written criteria for one kind of interface artifact that an eval agent scores an instance against, item by item.
- Example :: "we'll need to provide them with relevant rubricks they can record their evaluations against."
- Avoid :: checklist, criteria alone
- Specs :: skill-evals

* eval agent
An agent that evaluates what a step left, against the case's expected result and the rubric for its kind of artifact, and audits each of the case's checks; it takes no part in the step it evaluates and changes no verdict. Revised 2026-11-12 (the evals' spec revision); until then it evaluated against a rubric only.
- Example :: "eval agents will need to examine the artifacts."
- Avoid :: judge (the sources' word), Reviewer (a role of the skill)
- Specs :: skill-evals

* regression set
The fixed cases a skill change must pass before it is installed; expected to pass near 100% on the installed skill.
- Example :: its absence: "the cycles we use to evaluate a skill change are never the same."
- Avoid :: test suite, benchmark
- Specs :: skill-evals

* advisory set
Cases run beside the regression set whose result is reported and blocks nothing; where what is not yet reliable is measured.
- Example :: "gate the install with an advisory set alongside."
- Avoid :: soft gate, capability set (the sources' word)
- Specs :: skill-evals

* step
One piece of work one agent does between receiving its input and handing back.
- Example :: "many if not most or all of the steps taken by skill roles can be run with some kind of constructed mock input."
- Avoid :: phase (a phase holds many steps), task (a unit of the change's work)
- Specs :: skill-evals

* case
One eval: it cites the scenarios it tests, names the step where they are observed and the step's input, states its expected result, and holds the checks applied to what the step left. Revised 2026-11-12 (the evals' spec revision); until then it named one outcome or one rule.
- Example :: the dispatcher's first step on a change whose cycle has closed, checked for a spawn of the plan phase agent.
- Avoid :: test (a product's), scenario (a spec's)
- Specs :: skill-evals

* trial
One run of a case. A case is run more than once because two runs of the same step on the same input differ.
- Example :: "let measured agreement set the trials."
- Avoid :: run alone (a replay is also run), attempt
- Specs :: skill-evals

* fixture
What a step needs besides its interface artifact in order to run: a checkout of the code at a commit for an Implementor or a Reviewer, a home with its record for a phase agent or the dispatcher.
- Example :: a clone of a home at the commit where a cycle closed.
- Avoid :: snapshot, stand-in (the testing skill's word, for a fake of a real thing), mock
- Specs :: skill-evals

* fixture library
The static files and git repositories fixtures are copied from, kept apart from the cases that explain what they plant. Agreed 2026-11-12 in the review of how the evals work.
- Example :: "we want to prefer a library of static text (including git repos) instead of generating things all the time"
- Avoid :: fixture builder, snapshot
- Specs :: skill-evals

* audit
An eval agent's reading of one check in one trial, given the scenario it rests on, how it is computed, what it observed and the item of the expected result it serves: does the check, as computed, observe what the item expects? /agrees/, or /suspect/ with a reason. It never changes the check's verdict; a suspect check goes to a person. Agreed 2026-11-12 in the review of how the evals work; revised 2026-11-13 (D11), when checks came to read only what a spec fixes and the audit stopped being given the skill's change between two trees.
- Example :: "instructing the evaluating agent to consider the results of the check in context of the desired change and how the check is performed"
- Avoid :: override, re-judge, review (a role of the skill)
- Specs :: skill-evals

* validation
A person's reading of one trial of a case, in full, against each of its checks, items and audits, recorded with the commit it was made at (the case's =:VALIDATED:=). The case's trials count only while what runs of it is unchanged since that commit. Agreed 2026-11-13, in place of "hand reading".
- Example :: "the phrase “Hand reading” is strange, can we name this better?"
- Avoid :: hand reading, review (a role of the skill), calibration (suggests tuning), sign-off
- Specs :: skill-evals

* reference skill
The version of =orchestrate= a spec is extracted from: the current, working skill at a named commit, whose behaviour the spec first states. Agreed 2026-11-12 in the reopened research effort.
- Example :: "we are taking the current orchestration skill as a known working baseline to start from"
- Avoid :: baseline (=flows/execute.md='s word for the test run captured before merging), golden

* extraction record
The file, one per capability, in the research effort =research/skill-evals/extraction/= that shows where each statement backfilled into that capability's spec came from: the outcome ids, its provenance and its quotes from the reference skill. Frozen when the capability's spec is accepted; the spec never depends on it. Agreed 2026-11-12.
- Example :: =extraction/execute.org=, whose entry for "execute § Only merging stops" quotes =flows/execute.md= § 4 on both trees.
- Avoid :: basis, evidence (a research effort's agent files)

* gap
A behaviour a spec needs that the reference skill does not state: noted in the spec's =* Gaps= section, and never a requirement or scenario until the user decides it. Agreed 2026-11-12.
- Example :: what becomes of the merge that broke a test, while the user decides the regression ask.
- Avoid :: missing rule, TODO

* provenance
Whether a statement backfilled into a spec is =extracted= (the reference skill states it), =inferred= (our reading of it, reviewed by the user) or =filled= (a gap the user decided); recorded in the extraction record, not in the spec. Agreed 2026-11-12.
- Example :: "execute § A regression is recorded against its task" is =inferred=: the two trees record it differently.
- Avoid :: confidence

* home
The directory, with its own git repository, that holds a project's orchestrator configuration and
every change's process artifacts; usually a workspace above one or more repositories, sometimes a
repository's own root.
- Example :: "committed in the home with a subject naming its id"
- Avoid :: workspace (main's word for the usual shape of a home, not for the home itself), repo root, =$ORCH_HOME= in prose
- Specs :: execute

* code root
The change's own worktree of its repository, on the change's integration branch: where task
worktrees branch from, where tasks are merged and tested, and where code and the change's
documents (specs, intent, design) are committed.
- Example :: "merged, reviewed code on the change's integration branch, in its code root"
- Avoid :: repo, checkout, the change's worktree (true but confusable with a task's worktree), =$CODE_ROOT= in prose
- Specs :: execute

* change
One piece of work on one repository toward the goals its intent states, carried from opening
through one or more cycles to done; it has its own integration branch, its own worktree and its
own directory in the home.
- Example :: "the change's integration branch"
- Avoid :: proposal (OpenSpec's word, still in =externalisation.md=), feature, project
- Specs :: execute

* cycle
One pass of plan, execute and integrate over a change; a change runs as many cycles as its work
needs, each with its own id.
- Example :: "once in each cycle before any merge (the baseline)"
- Avoid :: iteration, sprint, round (main's "design round" runs before any cycle), wave (main uses it once, loosely, for a batch)
- Specs :: execute

* batch
The set of tasks plan composes for one cycle, which that cycle's execute phase implements.
- Example :: "turns a cycle's batch into merged, reviewed code"
- Avoid :: wave, sprint, task list
- Specs :: execute

* integration branch
The branch named after the change, in the change's repository, that each of its tasks merges into
and on which its tests run.
- Example :: "merged into the change's integration branch"
- Avoid :: main, the trunk; workspace integration branch (another branch: the one several changes of one repository share and merge into when done)
- Specs :: execute

* worktree
A separate checkout of the change's repository on a branch of its own. In the execute spec it is
always a task's worktree: cut from the integration branch for one task, where that task's
Implementor works, kept or removed as the task ends.
- Example :: "its worktree is kept"
- Avoid :: checkout (main's word for the Reviewer's), sandbox, workspace
- Specs :: execute

* the change's directory
The change's place in the home that holds its process artifacts: its state, its cycles' directories,
its inbox, its task files, its hardening list and the test outputs.
- Example :: "its output is kept in the change's directory in the home"
- Avoid :: change dir, =<change-dir>=, =$ORCH_CHANGE_DIR= in prose; the change's docs (that is the record in the code root)
- Specs :: execute

* the cycle's directory
The directory, inside the change's directory, that holds one cycle's artifacts: the briefs, the
Implementors' reports, the reviews, the applied asks, the handover and, once the cycle closes, its
archived state.
- Example :: "saved in the cycle's directory in the home"
- Avoid :: cycle archive (main's heading for it, which suggests it is written only at close), =cycles/<id>/=
- Specs :: execute
