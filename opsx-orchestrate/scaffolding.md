# Scaffolding contract

Scaffolding is the **executable form** of speculated register entries: files the Architect generates during plan-phase forward-mode that pin contracts as code rather than prose. They live in a quarantined directory (`<change>/scaffolding/`), are explicitly licensed for revision by Implementors, and are reconciled at integrate by treating their diffs as evidence for status transitions.

The motivating failure: the prior `architecture.md` artifact described system structure as prose. Prose drifts; tests don't. Scaffolding promotes a register entry's `validator` and `test_corpus` fields — currently embedded YAML strings — to actual files exercised by CI, *for the tiers where the cost-leverage ratio justifies it*.

## What scaffolding is — and is not

Scaffolding **is**:

- **Failing tests** asserting speculated invariants ("handlers fire exactly once per simple command").
- **Type signatures / interfaces / function shells** declaring boundary contracts (the canonical mapping between module A's output and module B's input, with a TODO body).
- **`pcase` / match scaffolds** enumerating speculated vocabularies — every value listed as an `error "TODO: handle :foo"` arm so unhandled values fail loudly at runtime instead of silently falling through.
- **Constructor + destructor exercises** for shape entries (opt-in tier; see below).

Scaffolding **is not**:

- **Implementations.** Bodies that satisfy the contract are the Implementor's job. The Architect generates the assertion; the Implementor makes it true.
- **Production code.** Scaffolding lives under `<change>/scaffolding/`, not `src/` and not `test/`. Promotion to a permanent home is an integrate-phase decision.
- **Authority.** Implementors hold a standing licence to rewrite scaffolding when they have justification. A rewrite is a *signal* at integrate, not a transgression.

## Tier selectivity

Not every register tier benefits equally from scaffolding. The defaults reflect where executable form catches things audit can't:

| Tier | Scaffold by default? | Rationale |
|---|---|---|
| **invariant** | Yes | The "asserted in prose, never tested" failure mode (signal-class 8). Highest leverage. |
| **vocabulary** | Yes | A `pcase` scaffold listing all speculated values catches dispatch holes at runtime, not via late audit. |
| **boundary** | Yes | One canonical mapping function shell eliminates per-implementor reshape duplication (signal-class 4). |
| **shape** | Opt-in | The register entry's `validator` + `test_corpus` already encode this. Promote to a file when the validator is non-trivial OR ≥2 producers cross a module boundary; otherwise the YAML is enough. |

Per-project overlay adjusts defaults via `scaffolding.tiers`. Shape-tier is opt-in because the marginal value is low and the duplication cost (validator in YAML *and* in a file) is real. **Implementations of the actual code under test are never scaffolded** — that's Implementor turf and crystallises too early.

## Quarantine: where scaffolding lives

```
openspec/changes/<change>/
  proposal.md
  design.md
  specs/...
  tasks/
  scaffolding/                          # NEW
    invariants/<entry-id>.<test-ext>
    vocabularies/<entry-id>.<ext>
    boundaries/<entry-id>.<ext>
    shapes/<entry-id>.<ext>             # opt-in
```

Per-language path conventions resolve via the overlay (`scaffolding.directory`, `scaffolding.layout`).

The quarantine is load-bearing: scaffolding is **in the change**, not in `src/`. When the change merges, each scaffolded file takes one of three dispositions (set at integrate; see *Reconciliation* below):

- **Promoted** — the file migrates to its permanent home (`test/`, the target module). Promotion is itself a follow-up task generated by integrate.
- **Archived** — enforcement landed via a different mechanism (e.g. a runtime check); the scaffold's job is done.
- **Rejected** — the speculation was wrong; the scaffold is deleted and the register entry transitions to `divergent`.

A scaffolded file never silently follows the change into `src/`. Every file gets a disposition.

## Failing-stub discipline

A scaffolded test that passes trivially is worse-than-useless: it gives green-light cover with no assertion. Scaffolded tests **must fail loudly** until an Implementor satisfies them.

Per-language style, configurable via `scaffolding.failing-stub-style`:

| Style | Typical languages | Mechanism |
|---|---|---|
| `error-call` | elisp, lisp, scheme | `(error "speculated; not implemented")` in the test body |
| `xfail` | python, rust | `@pytest.mark.xfail(strict=True)`, `#[should_panic]` |
| `compile-fail` | rust, ts (strict mode), kotlin | Function/type signature with no body; compilation fails until satisfied. Preferred where supported — strongest possible failure. |
| `strict-skip` | go, ts, java | `t.Skip("speculated; not implemented")` / `test.todo(...)` / `@Ignore` — but **CI fails if a strict-skip survives an integrate phase**. The integrate exit gate enumerates strict-skipped scaffolds as un-dispositioned. |

The baseline test snapshot at the start of execute (`<repo>/.orchestrator/baseline-<cycle-id>.txt`) records the failing scaffolds as expected-failures. The cycle's job is to flip them green (or revise them, or reject the speculation outright).

A scaffold the task didn't cite that nonetheless flipped green is itself a finding — typically `dead-branch` (signal-class 6) or accidental coupling. Surfaces in the end-of-cycle Architect audit.

## Each scaffolded file ties back to a register entry

Every file under `<change>/scaffolding/` carries a header (per-language comment syntax) naming its origin entry:

```
# scaffolding-of: register/invariant/handlers-fire-once
# generated-at: 2026-04-29T14:32:11Z
# license: implementor-may-revise
```

The orchestrator parses these headers at execute and integrate to map diffs back to entries. A scaffolded file with no `scaffolding-of` header is a state-file bug — the integrate gate refuses to close.

The register entry, in turn, gains a `scaffolding_path` field on its template:

```yaml
scaffolding_path: openspec/changes/<change>/scaffolding/invariants/handlers-fire-once.test.el
scaffolding_status_at_integrate: untouched | modified | rejected | promoted | archived
```

When a tier is in `scaffolding.tiers`, the entry's existing `validator` / `test_corpus` YAML fields are **omitted** in favour of the scaffolded file. When the tier is opted out, the YAML fields remain in their existing form. Two encodings of the same contract is a defect.

## Forward-mode hand-off

Scaffolding generation is **a defining operation of plan-phase forward-mode** (per `flows/plan.md` step 2 and `roles/architect.md` § Forward-mode), not a separate phase or trigger. It runs immediately after the Architect populates a speculative register entry, gated by tier:

1. Architect writes/revises the speculative register entry (existing forward-mode operation).
2. If the entry's tier is in `scaffolding.tiers` for this project, Architect generates the scaffolded file in the change's `scaffolding/` subtree.
3. The file's path is recorded on the entry as `scaffolding_path`; the file's `scaffolding-of` header points back to the entry.
4. Implementor briefs assembled in plan step 5 cite scaffolding paths alongside register-entry text.

The Architect's read-only-against-code constraint is preserved: scaffolding lives in the quarantine, not `src/` and not `test/`. The Architect does not modify any pre-existing file in any phase.

## Implementor brief framing

The brief surfaces scaffolding with explicit revision licence:

> The Architect generated `<change>/scaffolding/<tier>/<entry-id>.<ext>` from the speculated register entry `register/<tier>/<entry-id>`. **This is speculation, not authority.** Make the scaffolded test pass *or* revise the scaffold (and explain the revision in your `## Discoveries` section) *or* escalate to the orchestrator if the speculation is wrong at a level your task can't resolve. Modifying scaffolding is a signal, not a transgression.

This framing is fixed; project overlays do not soften it. A speculation that can't be pushed back on isn't speculation — it's commitment masquerading.

## Integrate-phase reconciliation by diff

The integrate phase's reconciliation step (per `flows/integrate.md` step 1) treats scaffolding diffs as **evidence** for the register-entry status transition:

| Scaffolding diff during execute | Register entry transitions to | Reconciliation note carries |
|---|---|---|
| Untouched + scaffold green at end of cycle | `confirmed` | "Scaffold passed unchanged. Speculation matched." |
| Modified by Implementor + reviewer accepted | `reconciled` | `prior_form` (pre-diff), `new_form` (post-diff), and the mandatory `why_tests_missed` line — the diff is its own substrate |
| Modified by Implementor + reviewer rejected | `divergent` | `divergence_evidence`: the rejected modification; `escalation: architect \| user` |
| Promoted to permanent location | `confirmed` (with `scaffolding_status_at_integrate: promoted`) | Promotion task generated by integrate; note records target path |
| Archived (enforcement landed via different mechanism) | `confirmed` (with `scaffolding_status_at_integrate: archived`) | Note records *where* enforcement actually lives (e.g. runtime-check at file:fn) |
| Strict-skip still skipping | (gate failure — un-dispositioned) | Integrate refuses to close until disposition is set |

The mandatory `why_tests_missed` line on `reconciled` entries gets concrete substrate — the diff itself — rather than the Architect's narrative reconstruction. Reconciliation moves from judgment to mechanical classification, with the Architect's prose layer reduced to "what pattern does this diff exemplify, for the meta-discoveries field?"

## State-file extensions

The state file's `register_touched` entry (per `state.md`) gains:

```json
{
  "entry_id": "register/invariant/handlers-fire-once",
  "scaffolding_path": "openspec/changes/<change>/scaffolding/invariants/handlers-fire-once.test.el",
  "scaffolding_diff_status": "untouched | modified | rejected",
  "scaffolding_status_at_integrate": "untouched | modified | rejected | promoted | archived"
}
```

`scaffolding_diff_status` is observed during execute (after each merge) by inspecting the diff against the merge-base for the scaffolding subtree. `scaffolding_status_at_integrate` is set during integrate's reconciliation step. Both null on a tier that opted out of scaffolding for this project.

## Phase-gate extensions

**Plan exit gate** gains:

| Check | Condition |
|---|---|
| `scaffolding_generated_for_tiered_entries` | Every speculated entry whose tier is in `scaffolding.tiers` has a `scaffolding_path` set and the file exists with a valid `scaffolding-of` header |

**Integrate exit gate** gains:

| Check | Condition |
|---|---|
| `all_scaffolding_dispositioned` | Every scaffolded file in the cycle has `scaffolding_status_at_integrate` set to one of `promoted` / `archived` / `rejected` (transient `untouched` / `modified` is not a final disposition) |

## Overlay configuration

The project overlay (per `overlay.md`) gains a `scaffolding` block:

```yaml
scaffolding:
  enabled: true                                  # default; false disables entirely
  tiers: [invariant, vocabulary, boundary]       # default; add `shape` to opt in
  directory: scaffolding                         # relative to <change>/
  failing-stub-style: error-call                 # see Failing-stub discipline table
  layout:
    invariant: invariants/<entry-id>.test.el
    vocabulary: vocabularies/<entry-id>.el
    boundary: boundaries/<entry-id>.el
    shape: shapes/<entry-id>.test.el             # only if shape ∈ tiers
```

When `scaffolding.enabled: false`, the orchestrator behaves as today — register entries carry `validator` and `test_corpus` in YAML; no scaffolding files; the plan and integrate gate checks for scaffolding are no-ops. Useful for projects in languages where stub cost exceeds leverage (deeply dynamic environments where any signature is a stub).

## What this displaces

- **The old `architecture.md` artifact** (now removed from the openspec schema). Its *Testing Approach → Scenario Mapping* section was prose attempting what scaffolding does as code.
- **The register entry's `validator` and `test_corpus` YAML fields**, when promoted. Both fields remain valid for the case where scaffolding isn't generated (shape-tier opt-out, or the entry is purely documentary).
- **Architect signal-class 8 (`invariant-gap`) for in-cycle contracts.** Speculated invariants ship with their tests; the asymmetry can't form for new entries. Legacy invariants without scaffolding remain in scope for the audit.

## Cost calibration

Scaffolding adds plan-phase work. Defaults are deliberately tier-restricted to keep the cost in proportion to leverage:

- **invariant**: a few-line failing test per entry; cheap.
- **vocabulary**: a `pcase` / match scaffold; modest.
- **boundary**: one mapping-function shell per boundary; modest.
- **shape (opt-in)**: a constructor + destructor exercise; small but duplicates the YAML validator field.

Worth measuring on the first migrated project (VCE) before generalising the cadence — same cost-calibration concern as the between-cycle Architect audit.

## Failure modes to watch

- **Premature crystallisation.** A scaffold the Implementor can't push back on becomes hidden authority. Mitigation: the brief's revision-licence framing is fixed (no overlay softening); reviewer rejecting an Implementor's scaffold revision must produce its own register-entry-divergence note, not just "rejected."
- **Scaffolds that become tests-of-tests.** A failing scaffold is fine; a passing scaffold no one revises is dead weight. Mitigation: every scaffolded file gets a disposition at integrate (promoted / archived / rejected); none survive un-dispositioned into the next cycle.
- **Tier creep.** A project enabling shape-tier scaffolding by reflex means duplicating the YAML validator into a file unnecessarily. Mitigation: shape-tier defaults to opt-in, and the overlay carries an explicit comment line on `tiers:` reminding why shape isn't there.
- **Language-asymmetric leverage.** TS/Go/Rust get cheap stubs; deeply dynamic languages get expensive stubs. Mitigation: per-project `scaffolding.enabled: false` is a first-class option, and `failing-stub-style` is configurable per project.
